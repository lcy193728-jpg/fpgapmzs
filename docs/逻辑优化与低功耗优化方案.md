# 逻辑优化与低功耗优化方案

> 对象：嵌赛 2026 安路赛道选题一「基于安路 EG4S20 的 HDMI 多媒体播放系统」  
> 工程：`_dev_sim_0b18789/audio_final`（顶层 `integrated/top_final.v`）  
> 基线：**10-3 版**（位流 `artifacts/pic_sdram_audio_final_v10-3.bit`，SHA-256 `a8c0c935…`，git `e32809c`）  
> 器件：安路 EG4S20BG256 ｜ EDA：TD 6.2.168116  
> 参照标准：《小鹅通 17 讲》讲义 + 配套源码（118 个 `.v`）  
> 编制日期：2026-10-03

## 0. 结论速览

| 维度       | 当前水平                                            | 主要症结                                                  | 最高性价比动作                             |
| -------- | ----------------------------------------------- | ----------------------------------------------------- | ----------------------------------- |
| **逻辑优化** | 中上（模块化好、容错完备；但**存在资源误用与架构性冗余**）                 | ① 8KB 字库被综合成 LUT ② SD 取图靠魔数扫描 ③ 4 场景 OSD 串行叠加、各自全画布比较 | **L1** 修字库 ROM（省 ~500 LUT）          |
| **低功耗**  | 中（ROM 读、消隐期已做门控；但**缺 operand isolation 与资源释放**） | ① 6 个全局时钟网络常开 ② 55 块 BRAM 全时供电 ③ 非活动场景逻辑仍全速翻转         | **P1** operand isolation（改动最小、收益最大） |

**一句话结论**：本设计的瓶颈不是"逻辑写错了"，而是 **LUT 89.74% 与 BRAM 98.44% 的双满仓**，而 **32K BRAM 只用了 3/16**。因此优化的主轴应是「**把误用成 LUT/9K-BRAM 的东西搬到闲置的 32K BRAM 上**」，同时用 operand isolation 把非活动场景的动态功耗压下去——这两条都不动功能、不改时序收敛。

## 2. 逻辑复杂度瓶颈分析

### 2.1 【确诊】8KB 字库被综合成 LUT —— 白扔约 500 LUT

**证据**：`meeting_glyph_rom.v:2-3`

```verilog
module meeting_glyph_rom(input [11:0] addr, output [15:0] q);
reg [15:0] mem[0:4095]; /* fehdl force_ram=1, ram_style="bram" */
```

- 容量 4096×16bit = **8KB**（约 64Kb）u0 3frq
- 层次报告：`font | meeting_glyph_rom | le 502 | lut 502 | bram 0`

**根因**：该模块是**纯组合读**（端口里没有 `clk`，输出不是 `reg`）。而片上 BRAM 只有**同步读**（读地址要过时钟沿）。因此综合器**无法**用 BRAM 实现它，那句 `force_ram=1` 属性形同虚设，只能吐出 502 个 LUT 当"分布式 ROM"。

**对照证明这不是器件限制**，而是写法问题——同工程另两个字库都正确进了 BRAM：

| ROM                       | 端口                                               | 结果                    | 判定           |
| ------------------------- | ------------------------------------------------ | --------------------- | ------------ |
| `osd_font_rom.v`          | `clk / rst / rd_en / addr / output reg [31:0] q` | 292 LUT + **25 BRAM** | ✅ 同步读，正确     |
| `emergency_font_rom.v`    | （带时钟）                                            | 14 LUT + **4 BRAM**   | ✅ 正确         |
| **`meeting_glyph_rom.v`** | **`addr / q`（无时钟）**                              | **502 LUT + 0 BRAM**  | ❌ **异步读，误用** |

**代价**：502 LUT ≈ 全设计 LUT 的 **2.9%**。在 89.74% 的占用下，这是最"冤"的一块。

### 2.2 【确诊】SD 取图仍是"魔数扫描"，架构上仍是"一卡一布局"

**证据**：`bmp_read_auto.v:23-26`

> 不解析 FAT 文件系统，从分区起点每 8 扇区(4KB 簇)跳读检查文件头 "BM"+分辨率白名单...

配合顶层**硬编码**分区常量（`Z_MENU_START=15936` / `Z_WEL_START=15936` / `Z_MEET_START=8512` / `Z_QUIZ_START=10368` / `Z_ALARM_START=10368`）。

**这正是小鹅通第七讲开篇点名批评的五宗罪**：

> ①不认识文件系统→误判 ②无 FAT 链→碎片读取错误 ③扫描范围只有前 64MB→大卡扫不到 ④无目录遍历→找不到子目录 ⑤仅靠魔数→**容易误判**（其他数据里有 "BM" 就被当成图片 → **花屏**）

**本项目已实际踩中第 ⑤ 条与"卡一变就全错"**：换卡（F: exFAT → G: FAT32）后所有 `Z_*` 失效、上电花屏；分区偏移从 2048 变 64 又让全部 `Z_*` 偏大 1984 扇区。**这是一类根因，不是一次性 bug。**

**逻辑代价**：`bmp_read_auto` 2114 le / 1525 LUT / **470 ripple**（32 位比较器密集：`bmp_len_cnt < file_len`、`pixel_count` 计数、9 项头校验）。

### 2.3 4 场景 OSD 串行叠加，每层各自重建坐标

顶层叠加链是**串联**的（`top_final.v:894` 起）：

```
osd_engine → osd_menu → osd_welcome → osd_scene → meeting_osd → emergency_multi_overlay → audio_viz_overlay → display_adjust
```

各层合计 LUT：osd_menu 364 + osd_welcome 459 + osd_scene 836 + meeting_osd 3054 + emergency 845 + viz 260 + adjust 546 ≈ **6364 LUT**。

**优点**（已做对的）：三路 OSD 字形窗**互斥**、共享一片 `osd_font_rom`、每层都有 `rom_en_o` 只在该层窗口内才读 ROM。

**代价**：

- 每层独立做"像素坐标是否落在我的窗口内"的比较（这就是 ripple 的来源：osd_scene 516 / osd_welcome 264 / display_adjust 253）
- 链路延迟串联累加（每层 1~3 拍）
- 每层都要把 24bit 像素流往下透传一次

### 2.4 进位链密度高（ripple 3384）

`osd_scene` 516 + `bmp_read_auto` 470 + `meeting_osd` 276 + `osd_welcome` 264 + `display_adjust` 253。

这些进位链集中在"大范围坐标比较"与"32 位计数/比较"上。它们虽在 25MHz 域不违例，但**是 place seed 高度敏感的直接原因**——本次事故就是"一行 wire 的改动改变布局 → 一条 SD 域路径（`bmp_read_auto.v:380` 的 32 位比较）被挤到擦边 → 图片读错 → 花屏"。**降低进位链密度 = 直接提升布局鲁棒性。**

## 3. 执行效率瓶颈分析

| #  | 瓶颈                        | 现状                                                  | 影响                              |
| -- | ------------------------- | --------------------------------------------------- | ------------------------------- |
| E1 | **SDRAM 单读端口 + 双缓冲**      | `frame_read_write` 只有 BUF0/BUF1 两块，缓冲池仅 4 块 9K BRAM | 切图/切场景必须重新加载整帧（数百 ms），无法"零延迟切换" |
| E2 | **魔数扫描命中率低**              | 每 8 扇区跳读一次，一次全分区扫描要过几十至几百个候选点                       | 冷启动/换场景首次出图慢                    |
| E3 | **OSD 串联链延迟累加**           | 7 级串联，每级 1~3 拍                                      | 约 10+ 拍流水延迟；坐标要多级随动同步           |
| E4 | **video_clk 域堆了 37% 的逻辑** | 5281 LUT 全在 25MHz 域                                 | 大量逻辑用不到的速度被全额实现，面积（而非时序）成为瓶颈    |
| E5 | **缩放为全档位双线性**             | `bmp_scale` 9 DSP / 9 BRAM（3 条 640 宽行缓存）            | 简单 2× 整数倍缩放也走完整双线性，性价比不高        |

**已做对、无需改的**（避免重复劳动）：

- `bmp_scale` 的 **100% 档真 1:1 旁路**（完全不过插值状态机，保画质、省带宽、面积可裁剪）
- `bmp_read_auto` 已按小鹅通第五讲落地 **6 项容错**（9 项头校验 / 错误码 / 坏图快跳 / 500ms 无进展超时 / 像素完整性 / 重试1次后跳过）
- `frame_fifo_read/write` 已有 512 深异步 FIFO + burst 读写
- 每个时钟域一个 `reset_sync`、PLL 锁定参与复位源、跨域用 `sync_2ff`/toggle 同步

## 4. 功耗瓶颈分析

> ⚠ 前提：TD 未提供功耗分析报告（`reports/` 下只有 `_phy.area` 与 `_pr.timing`，`build-output.txt` 内无 power 项）。故以下为**基于结构与翻转率的结构性判断**，非实测数值。

FPGA 动态功耗 ≈ `Σ C·V²·f·α`（α 为翻转率）。可动的只有 **C（电容/资源量）** 与 **α（翻转率）**——V 与 f 由板级与功能决定。

| #   | 瓶颈                              | 现状                                                                             | 功耗机理                              |
| --- | ------------------------------- | ------------------------------------------------------------------------------ | --------------------------------- |
| P-1 | **6 个全局时钟网络常开**                 | video_clk(fanout 2532)、sd_card_clk(1471)、ext_mem_clk、hdmi_5x_clk、50M、SDRAM_CLK | 时钟树是 C 最大的一棵树，且 α=1（每拍必翻）         |
| P-2 | **55 块 BRAM 全时供电在 video_clk 域** | 占 63 块的 87%                                                                    | BRAM 有静态漏电 + 每次读的动态功耗；全满 = 漏电总量最大 |
| P-3 | **非活动场景逻辑仍全速翻转**                | 只有输出与 ROM 读被 `en` 门控（`rom_en_o`），内部坐标比较器/计数器仍随像素流翻转                            | α 高：约 4000 LUT 在每个像素拍做无意义运算       |
| P-4 | **SDRAM 控制器 + PHY 常开**          | 125MHz DDR 接口、持续刷新                                                             | 高频 + 大量 IO 翻转（不可避免）               |
| P-5 | **HDMI 5x 串化器常开**               | 125MHz 驱动 34 个负载（`hdmi_5x_clk`）                                                | 不可避免（要出 HDMI 就有）                  |
| P-6 | **数码管 200Hz × 8 位扫描**           | `seg_scan`：`SCAN_FREQ=200`、`CLK_FREQ=50M` → 每 31249 拍换一位                       | 8 根段线 + 8 根位线持续翻转，量小但持续           |
| P-7 | **13 块 32K BRAM 闲置**            | 3/16 使用                                                                        | 闲置块若未被综合器断电，仍有静态漏电（可控）            |

**已做对的低功耗设计**（值得肯定，无需改）：

- `osd_font_rom` 有 `rd_en`，`seg_scan` 与各 OSD 的 `rom_en_o` 都按需使能 → **ROM 读不是每拍都发生**
- `osd_scene` 的 `rom_en` 是**逐窗口精算**的组合逻辑（`osd_scene.v:373-462`），只在窗口内拉高
- 跨域参数只在帧边界锁存（`display_adjust` 的亮度/对比度档位），避免整帧抖动
- `bmp_scale` 100% 档旁路 → 该档下行缓存几乎静止
- `display_valid=0` 时黑屏（不写无意义数据）

## 5. 优化措施 —— 维度一：逻辑优化

> 收益按"对 LUT / BRAM / 时序鲁棒性"的影响估算；难度分 低 / 中 / 高。

### L1 ★ 把 `meeting_glyph_rom` 改成同步读 BRAM（最高性价比）

| 项        | 内容                                                                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **问题定位** | `src/meeting_glyph_rom.v:2` 无 `clk` 端口的组合 ROM，502 LUT / 0 BRAM                                                                                                                    |
| **具体措施** | ① 端口改为 `input clk, input [11:0] addr, output reg [15:0] q` + `always @(posedge clk) q <= mem[addr];` ② 读取侧（`meeting_osd` 内取字）地址**提前一拍**给出，数据晚一拍到（对齐方式与 `osd_font_rom` 完全相同，可直接照搬） |
| **预期收益** | **省 ~500 LUT**（89.74% → **≈87.2%**，为后续功能腾出空间）；BRAM9K 占用不变（改由 **32K BRAM** 承载：4096×16bit ≈ 2 块 32K，而 32K 尚余 13 块）                                                                  |
| **实现难度** | **低** —— 端口改造 + 取字打一拍，改动局限在两个文件                                                                                                                                                   |
| **取舍权衡** | 读延迟 **+1 拍**（需同步调整 `meeting_osd` 中与之配对的坐标/使能路径，保持同拍对齐）；占用 2 块 32K BRAM（不影响 9K 的 63/64）                                                                                            |
| **风险**   | 低。既有 `osd_font_rom` 就是同款写法，可直接对照                                                                                                                                                  |
| **验证**   | `run_sim_osd_scene` / `run_sim_display` 必须 0 FAIL（会议 OSD 字形位置不变）                                                                                                                  |

### L2 补齐/精简 `meeting_osd` 自身逻辑

| 项        | 内容                                                                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| **问题定位** | `meeting_osd` 除字库外仍有 **≈2252 LUT**，是全设计最大的单一逻辑块；ripple 276                                                 |
| **具体措施** | ① 排查同类"大范围坐标比较"是否可复用同一组比较结果；② 把 `meeting_fmt`（300 LUT，串行 BCD 格式化）中可共享的十进制分频链合并；③ 检查是否存在按 `state` 分支的重复窗口判断 |
| **预期收益** | 保守估计 **省 200~400 LUT**                                                                                     |
| **实现难度** | **中高** —— 需逐段分析，且会议场景功能面大，回归成本高                                                                            |
| **取舍权衡** | 与 L1 有重叠（L1 已吃掉 502 LUT），L2 属"锦上添花"；改动大会干扰已收敛的布局                                                           |
| **风险**   | 中。**建议在 L1 之后评估是否还必要**                                                                                     |

### L3 ★ SD 取图升级为 FAT32（架构级，对齐小鹅通第七讲）

| 项        | 内容                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **问题定位** | `bmp_read_auto` 用魔数扫描 + 顶层硬编码 `Z_*`（一节 2.2）                                                                                                                                                                                                                                                                                                                                                         |
| **具体措施** | 按小鹅通第七讲实现：① `fat32_volume_scanner`（解析 BPB，`fat_start_lba = partition_lba + reserved_sectors`、`data_start_lba = fat_start_lba + fat_count*fat_sectors`、`cluster_lba = data_start_lba + (cluster-2)*sectors_per_cluster`）；② `fat32_file_streamer`（按 FAT 链流式读，簇号定位全用移位：`fat_sector = fat_start_lba + (cluster>>7)`、`fat_offset = (cluster & 0x7F)<<2`）；③ 防 FAT 环 `MAX_VISITED_CLUSTERS`；④ 替换 `Z_*` 硬编码 |
| **预期收益** | **根治"换卡/改分区就花屏"这一整类问题**（赛题鲁棒性/完成度加分）；不再需要按卡手工维护 `Z_*`；碎片文件、大卡、子目录都能读                                                                                                                                                                                                                                                                                                                                |
| **实现难度** | **高** —— 新增 ~680 行 RTL + 需 512B 扇区回放缓冲（1 块 BRAM）+ 全套新 TB                                                                                                                                                                                                                                                                                                                                            |
| **取舍权衡** | **空间矛盾**：当前 BRAM9K 63/64 已满、LUT 89.74%。**必须先做 L1 腾出 LUT，并把 ROM 迁到 32K BRAM**，否则无从下手；相对而言，魔数扫描那部分 LUT 不一定能净省（FAT32 也有逻辑量），**收益主要是鲁棒性而非面积**                                                                                                                                                                                                                                                           |
| **风险**   | 中高。属于"换掉已验证通路"的大改，必须全量回归 + 上板实测                                                                                                                                                                                                                                                                                                                                                                     |
| **建议**   | **排在 L1 之后**；若时间紧，可作为"架构演进"章节写入答辩材料而不实际落地                                                                                                                                                                                                                                                                                                                                                           |


### L4 缩放按档位分算法（省 DSP）

| 项 | 内容 |
| --- | --- |
| **问题定位** | `bmp_scale` 9 DSP / 9 BRAM；所有缩放档都走双线性 |
| **具体措施** | 对小鹅通第五讲 `bmp24_decoder.average_four` 的**纯加法 2×2 均值**（3 次加法 + 常量 2 + 右移 2，**零 DSP**）用于 2× 整数倍降采样档；仅在非整数倍档保留双线性 |
| **预期收益** | DSP **9 → 约 4~5**（当前 14/29，余量本来就够，属"省着用"）；行缓存数量不变 |
| **实现难度** | **中** —— 需按 `res_level` 分派算法，新增一条数据通路 |
| **取舍权衡** | 2× 降采样档**画质下降**（均值 vs 双线性）；且增加一个 mux 层次 |
| **风险** | 低，但**收益有限**（DSP 不紧张）→ **优先级低** |

### L5 合并串行 OSD 链（不建议现在做）

| 项 | 内容 |
| --- | --- |
| **问题定位** | 7 级串联叠加，各层重复坐标重建（一节 2.3） |
| **具体措施** | 把 menu/welcome/scene 的窗口判断合并进一个"统一叠加引擎"，共享一组坐标比较器 |
| **预期收益** | 理论可省 **500~1000 LUT** + 减少 ripple |
| **实现难度** | **高**（牵动 4 个已验证模块 + 全部 OSD 回归） |
| **取舍权衡** | 收益大但风险高、工期长；**在 L1~L3 未完成前不动** |

### L6 降低进位链密度（提升布局鲁棒性）

| 项 | 内容 |
| --- | --- |
| **问题定位** | ripple 合计 3384；`bmp_read_auto.v:380` 的 `bmp_len_cnt < file_len`（32bit 比较）已被证实为**本次花屏事故的敏感点** |
| **具体措施** | ① 对"只在一个状态下有效"的长比较加**使能门控**（`en ? (a<b) : 1'b0`），让综合器有操作数隔离的机会；② 对 32 位比较尽量改"高位先比、低位后比"的分段结构；③ 大范围坐标比较改为"行区间状态机"（进入/退出事件驱动）而非每拍全量比较 |
| **预期收益** | 不直接省 LUT，但**显著降低 place seed 敏感度**——本次事故的直接教训就是"布局一挪就坏" |
| **实现难度** | **中**（逐点改造，需比对时序报告验证） |
| **取舍权衡** | 可能略增 LUT（门控本身要资源）；收益体现在"不再随机踩雷" |
| **风险** | 低（每改一处都需重扫 seed + 上板验证） |

## 6. 优化措施 —— 维度二：低功耗优化

> 原则（小鹅通第六讲/第八讲/第十一讲一致）：**不要用逻辑门去"门控时钟"**（TD 不推荐、易出毛刺、破坏时钟树）。低功耗一律走「**使能释放 + 数据保持**」两条路。

### P1 ★ Operand Isolation：把非活动场景的输入"钉死"（首选）

| 项 | 内容 |
| --- | --- |
| **问题定位** | 只有输出与 `rom_en` 被 `en` 门控；`osd_menu`/`osd_welcome`/`osd_scene`/`meeting_osd` 内部的坐标比较器、计数器仍随像素流**全速翻转**（合计 ≈4000 LUT） |
| **具体措施** | 在各模块**入口**对操作数做门控，例如：`wire [10:0] px_x_g = scene_en ? px_x : 11'd0;`、`px_y_g = scene_en ? px_y : 11'd0;`，模块内部一律用 `_g` 版本。使能关闭时输入恒定 → 下游组合逻辑不再翻转（综合器可识别为静态，进而优化/省翻转） |
| **预期收益** | 非当前场景的 OSD 逻辑动态功耗 **≈降 60~80%**（这些模块占 25MHz 域的绝大多数）；因每场景**只有一路在用**，平均可压掉约 **3/4 的 OSD 翻转** |
| **实现难度** | **低** —— 每个模块入口加几个 2:1 mux，不动内部逻辑 |
| **取舍权衡** | 增几十个 LUT；但换来的翻转下降远大于此。**不改时钟树、不改时序收敛方式** |
| **风险** | 低。注意：被门控的坐标若同时用于"输出对齐"，需保证门控只作用于**比较用的副本**，透传路径仍用真实坐标 |
| **验证** | OSD 各场景回归 0 FAIL；上板确认切换场景画面正常 |

### P2 ★ 释放 BRAM：把字模搬到闲置的 32K BRAM

| 项 | 内容 |
| --- | --- |
| **问题定位** | `bram9k` 63/64 满、而 `bram32k` 只用了 3/16。`u_osd_font_rom` 一家占 **25 块 9K**（5856×32bit ≈ 187Kb） |
| **具体措施** | ① 把 `osd_font_rom` 的 32bit 宽字模改为由 **32K BRAM** 承载（5856×32 ≈ 6 块 32K，而 9K 需要约 21~25 块）；② 同步把 L1 的 `meeting_glyph_rom` 也放 32K；③ 若工具不会自动回退，需用 TD 支持的属性/原语显式指定 |
| **预期收益** | 9K BRAM 占用从 **63 → 约 42~45**，**释放近 20 块 9K**；BRAM 静态漏电与动态功耗同步下降；同时为 L3（FAT32 需扇区缓冲）、后续新功能腾出空间 |
| **实现难度** | **中** —— 需先验证 TD 对 32K BRAM 的推断行为（是否接受属性、是否有宽度/深度限制） |
| **取舍权衡** | 若工具不支持自动选择，可能需改写 ROM 结构（如拆成 2 片 16bit 并行） |
| **风险** | 中。**必须先做小规模实验验证**，再动主链路 |
| **备注** | 这是"**同时降面积与功耗**"的最优项，与 L1 天然配套 |

### P3 计数器/地址冻结（小鹅通 §5.1/§5.2 原样落地）

| 项 | 内容 |
| --- | --- |
| **问题定位** | 空闲拍仍让 SDRAM 21 位地址总线、像素坐标计数器持续翻转 |
| **具体措施** | ① `frame_fifo_read/write` 的地址寄存器在非读写拍保持（`else App_rd_addr_r <= App_rd_addr_r;`）——**核查是否已做，缺则补**；② 一次性延时/上电脉冲类计数器达成条件后**永久停摆**（`<= S_cnt;`）而非继续累加；③ 消隐期把像素坐标计数器冻结 |
| **预期收益** | 省掉 21~24 位地址/坐标总线的持续翻转；对小鹅通示例工程实测是可观的项 |
| **实现难度** | **低** |
| **取舍权衡** | 几乎无。属纯 RTL 的"软门控"，不改时钟树 |
| **风险** | 低 |

### P4 数码管扫描降频

| 项 | 内容 |
| --- | --- |
| **问题定位** | `seg_scan.v:27` `SCAN_FREQ = 200`（8 位 → 每位 200Hz，整屏 25Hz 刷新） |
| **具体措施** | 降到 100~120Hz/位（整屏仍有 12.5~15Hz，无可见闪烁）；或在无变化时降低扫描占空 |
| **预期收益** | seg 段/位线翻转率降约一半（IO 功耗项，量级小） |
| **实现难度** | **极低**（改一个 parameter） |
| **取舍权衡** | 刷新率略降；**注意别降太低导致可见闪烁**（建议 ≥100Hz/位） |
| **风险** | 低 |

### P5 场景级模块冻结

| 项 | 内容 |
| --- | --- |
| **问题定位** | `quiz_ctrl`、`meeting_ctrl`、`scene_audio` 等非当前场景的控制逻辑仍在运行 |
| **具体措施** | 用 `scene_id` 生成各模块的运行使能，关闭时冻结其状态机与计数器（保持输出不变） |
| **预期收益** | 中（这些模块合计约 1500 LUT，占比较小） |
| **实现难度** | **中**（每个模块要单独确认"冻结不破坏状态"） |
| **取舍权衡** | 与 P1 思路一致，但收益小、改动多 → **优先级低于 P1** |
| **风险** | 中（冻结不当会导致场景切换时状态错乱） |

### P6 全局时钟网络审视（**建议只做核查，不做改动**）

| 项 | 内容 |
| --- | --- |
| **现状** | 6 个 Global 时钟在用；`U3/u2_ram/SDRAM_CLK` 报告 fanout=0（应仅驱动 SDRAM 输出时钟）；`clk_dup_1`（driver=io, fanout 74）是 50MHz 输入复制 |
| **可动性** | `hdmi_5x_clk`（125MHz 串化）与 `ext_mem_clk`（125MHz DDR）**必须保留**；`sys_pll` 的 C2（125MHz@180°）仅驱动 SDRAM_CLK，若确认内部无负载则其功耗已很小 |
| **结论** | ⚠ **小鹅通第二讲明确纪律："绝对不要乱动 PLL 配置和时钟频率，只在各自时钟域内修改逻辑。"** 因此**不建议**为省功耗去改 PLL/关时钟输出——收益不确定，风险极高 |
| **建议动作** | 仅做一次核查：确认没有"输出了但没人用"的 PLL 通道（如果有，且 TD 支持关断，再评估） |

### P7 降低 video_clk 域 BRAM 访问频次

| 项 | 内容 |
| --- | --- |
| **问题定位** | video_clk 域 55 块 BRAM（占 87%），`bmp_scale` 3 条行缓存是流式按需写、已优化；`osd_font_rom` 已按 `rom_en` 门控 |
| **具体措施** | ① 检查各行缓存在"无有效像素"（消隐期）是否仍在读；② 确认 `rd_en` 在消隐期不拉高 |
| **预期收益** | 小~中（BRAM 动态部分） |
| **实现难度** | **低** |
| **取舍权衡** | 无 |
| **风险** | 低 |

## 7. 优先级与实施路线

### 7.1 收益 × 难度矩阵

| 措施 | 维度 | 预期收益 | 难度 | 风险 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| **L1** 字库改同步读 BRAM | 逻辑 | **省 ~500 LUT** | 低 | 低 | **P0** |
| **P1** Operand isolation | 功耗 | **OSD 翻转降 60~80%** | 低 | 低 | **P0** |
| **P3** 计数器/地址冻结 | 功耗 | 中（省地址/坐标总线翻转） | 低 | 低 | **P1** |
| **P2** 字模迁 32K BRAM | 逻辑+功耗 | **释放 ~20 块 9K BRAM** | 中 | 中 | **P1** |
| **P4** 数码管降频 | 功耗 | 小 | 极低 | 低 | P2 |
| **L6** 降进位链密度 | 逻辑 | 提升布局鲁棒性 | 中 | 低 | P2 |
| **L2** meeting_osd 精简 | 逻辑 | 省 200~400 LUT | 中高 | 中 | P3 |
| **P5** 场景级冻结 | 功耗 | 中 | 中 | 中 | P3 |
| **L4** 缩放分档算法 | 逻辑 | DSP 9→5 | 中 | 低 | P3 |
| **L3** FAT32 替换魔数扫描 | 逻辑 | 根治换卡花屏 | 高 | 中高 | P4（需 P0/P1 腾空间） |
| **L5** 合并 OSD 链 | 逻辑 | 省 500~1000 LUT | 高 | 高 | P5（不建议） |
| **P6** 动 PLL/时钟 | 功耗 | 不确定 | — | 极高 | **不建议** |

### 7.2 建议实施顺序

```
第 1 步（P0，可同批做）
  ├ L1  meeting_glyph_rom 改同步读       → 省 ~500 LUT
  └ P1  各 OSD 入口 operand isolation    → 翻转大幅下降
     ↓ 两项均不动时钟树、不改功能，风险最低
     ↓ 仿真全量回归 0 FAIL → 重扫 place seed → JTAG/SRAM 上板亲验

第 2 步（P1）
  ├ P2  字模迁移 32K BRAM（先做小规模验证） → 释放 ~20 块 9K
  └ P3  地址/计数器冻结                      → 省总线翻转

第 3 步（P2，可选）
  ├ P4  数码管降频
  └ L6  降低进位链密度（针对 bmp_read_auto.v:380 等高危点）

第 4 步（视时间与资源）
  └ L3  FAT32（架构演进；答辩材料价值 > 当下降面积价值）
```

**每步的硬性门禁**（沿用本项目纪律）：
1. 先仿真：全量回归 **FAIL = 0**，新用例必须先在"修复前版本"上跑出 FAIL
2. 再构建：`SWNS/HWNS ≥ 0`，**且人工复核 `route.qor` 的 Hold WNS 与 violated H-PE**（现有闸门只 grep 报告头的两行，存在缺口）
3. 再上板：**先 JTAG/SRAM**，亲眼确认「图片 + 声音 + 数码管」三者，**最后才固化 Flash**
4. 每次 RTL 变化 → netlist 变化 → **必须重扫 place seed**（高占用下同一 seed 会退化）

## 8. 取舍权衡总表

| 措施 | 换来什么 | 付出什么 |
| --- | --- | --- |
| **L1** 字库同步化 | 省 500 LUT | 读延迟 +1 拍；占 2 块 32K BRAM |
| **P1** Operand isolation | OSD 翻转大幅下降 | 增几十个 2:1 mux（LUT 略增） |
| **P2** 字模迁 32K | 释放 ~20 块 9K BRAM，为后续功能腾空间 | 需先验证 TD 推断行为；ROM 结构可能需改写 |
| **P3** 计数器冻结 | 省地址/坐标总线翻转 | 无实质代价 |
| **L3** FAT32 | 根治换卡花屏、支持碎片/大卡 | ~680 行新 RTL、全套新 TB、占用 1 块 BRAM；**必须先用 L1+P2 腾出空间** |
| **L4** 缩放分档 | DSP 9→5 | 2× 档画质下降；多一层 mux |
| **L6** 降进位链 | 布局鲁棒性提升（不再"改一行就花屏"） | 可能略增 LUT；每点需重扫 seed + 上板 |
| **P6** 动 PLL | 理论省一个时钟网络 | **违反小鹅通明确纪律，风险极高 → 不做** |
