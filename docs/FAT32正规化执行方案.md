# FAT32 文件系统正规化执行方案（以小鹅通第七讲为蓝本）

> 目标：把工程当前「硬编码 Z_* 扇区号 + 魔数扫描」的 TF 卡读取方式，
> 升级为「FAT32 文件系统 + 目录项按文件名匹配 + FAT 链读取」的正规方式。
> 用户决定：① BMP 沿用现有文件名；② 会议配置 + 背景音乐也一并改成文件。
> 严格以小鹅通第七讲（第6课_FAT32文件系统升级）为第一标准。

---

## 一、现状盘点（已核实，勿改错地方）

### 1.1 当前 TF 卡素材（10 张 BMP + 2 类裸数据）

| 类别 | 素材 | 文件名 | 现定位方式 |
|---|---|---|---|
| BMP 会议底图 | 1 张 640×480 | `1_meet.bmp` | Z_MEET_START=8512 |
| BMP 抢答底图 | 1 张 640×480 | `2_quiz.bmp` | Z_QUIZ_START=10368 |
| BMP 备用 | 2 张 640×480 | `3_extra.bmp`、`4_extra.bmp` | 未入区 |
| BMP 迎新/菜单 | 6 张(320/640/1024 各2) | `w1_320a.bmp`…`w6_1024b.bmp` | Z_WEL_START=15936 |
| 会议议程配置 | 原始字节流(1272B, 3 扇区) | `MTG1`（裸扇区 200000） | mtg_start_sector 常量 |
| 背景音乐 | 裸 PCM 48k/16bit/mono | `wel_music_48k_mono.raw`（扇区 300000） | WAV_START_LBA 常量 |

### 1.2 当前 SD 读取链路（比小鹅通第七讲复杂）

```
sd_card_top(SPI底层, 与官方接口一致)
   └── sd_card_bmp
          ├── audio_sd_arbiter   ← 三路仲裁：图片 + 会议配置 + WAV 音频
          ├── bmp_read_auto(1219行)  ← 魔数扫描 + 分区重载 + 容错(9项校验/超时/重试)
          ├── meeting_sd_rd       ← 会议配置裸扇区读
          └── wav_stream_player   ← 音乐裸扇区流式读
```

**关键差异 vs 小鹅通第七讲：**
1. 小鹅通是「固定 PIC1~4.BMP，单使用者」，我工程是「多分区 + 三路 SPI 仲裁」。
2. 我的 `bmp_read_auto` 已含大量容错（9 项 BMP 校验、500ms 超时、坏图快跳、重试、
   多分辨率缩放 320/640/1024/1280）——这些是**已通过上板验证的资产，不能丢**。
3. 会议配置和音乐目前是「裸写扇区」，**不在文件系统内**。

## 二、正规化目标与范围

### 2.1 要正规化的（改用 FAT32 按文件名定位）
- ✅ BMP 图片 10 张：目录项匹配 + FAT 链读取，替代硬编码 Z_* 扇区号。
- ✅ 会议配置 MTG1：改成卡根目录的 `MTG1.CFG` 文件，按文件名定位。
- ✅ 背景音乐：改成卡根目录的 `WEL.BIN`（或保留 .raw），按文件名定位。

### 2.2 保留不动的（资产）
- ✅ `sd_card_top` SPI 底层驱动（与官方一致，接口不变）。
- ✅ `audio_sd_arbiter` 三路仲裁框架。
- ✅ `bmp_read_auto` 的**读图后半段**（BMP 头解析、9 项校验、多分辨率缩放、容错）。
- ✅ 会议配置解析、音乐流式播放。

## 三、核心设计

### 3.1 文件名约定（8.3 短名规范，关键！）

小鹅通第七讲明确：扫描器**只匹配 8.3 短文件名（大写）**，不支持长文件名(LFN)。
当前文件名 `w1_320a.bmp`（9 字符主名）**超长**，`wel_music_48k_mono.raw` 更超。
**必须重命名为 8.3 短名**。建议映射表：

| 现文件名 | 8.3 短名 | 场景 |
|---|---|---|
| `1_meet.bmp` | `MEET.BMP` | 会议底图 |
| `2_quiz.bmp` | `QUIZ.BMP` | 抢答底图 |
| `w1_320a.bmp` | `WEL1.BMP` | 迎新第1张 |
| `w2_640a.bmp` | `WEL2.BMP` | 迎新第2张 |
| `w3_1024a.bmp` | `WEL3.BMP` | 迎新第3张 |
| `w4_320b.bmp` | `WEL4.BMP` | 迎新第4张 |
| `w5_640b.bmp` | `WEL5.BMP` | 迎新第5张 |
| `w6_1024b.bmp` | `WEL6.BMP` | 迎新第6张 |
| `3_extra.bmp`/`4_extra.bmp` | `EXT1.BMP`/`EXT2.BMP` | 备用 |
| 会议配置 MTG1 | `MTG1.CFG` | 会议议程 |
| 背景音乐 raw | `WEL.BIN` | 迎新音乐 |

> 分辨率信息不再靠文件名，而是**由 bmp_read_auto 的 BMP 头解析**（它本来就会读宽高）。

### 3.2 模块划分（照搬小鹅通第七讲，3 个新模块 + 适配）

1. **`fat32_volume_scanner.v`**（照搬小鹅通，~400 行）
   - 读 LBA0 判断 MBR/直接引导 → 解析 BPB → 扫描根目录。
   - **改造**：`matching_resource` 的匹配表从 PIC1~4 扩展为**本工程全部素材名**
     （MEET/QUIZ/WEL1~6/EXT1~2/MTG1.CFG/WEL.BIN），输出每文件的起始簇号 + 大小。
   - 输出：`resourceX_cluster` + `resourceX_size` + 文件系统参数（fat_start/data_start/max_cluster/spc）。

2. **`fat32_file_streamer.v`**（照搬小鹅通，~200 行，几乎不改）
   - 按起始簇号 + FAT 链遍历，输出文件字节流（`file_valid/file_byte/file_byte_offset`）。

3. **`sd_sector_adapter.v`**（小鹅通 5.3 节，~80 行）
   - 把新模块的 `sector_*` 接口转到 `sd_card_top` 的 `sd_sec_*` 接口。
   - **改造**：本工程的 `sd_card_top` 已经输出 `sd_sec_read_data_valid/end`，
     但**没有** `sector_busy`/`sector_byte_index`/`sector_error` → 适配层需自生成。

4. **仲裁扩展**（本工程独有，小鹅通没有）：
   - 现有 `audio_sd_arbiter` 是 A(图片+会议)/B(音频) 两路。正规化后：
     - 扫描阶段：FAT32 扫描器独占（开机一次）。
     - 加载阶段：图片走 FAT32 流读器；会议配置走 FAT32 流读器（读 MTG1.CFG）；音频走 FAT32 流读器（读 WEL.BIN）。
   - **三路都变成 FAT32 流读器**，共用同一套 `sector_*` 接口 → 仲裁逻辑从
     「图片+会议 / 音频」改为「三个流读器分时复用 sd_sector_adapter」。

## 四、改造步骤（按依赖顺序，每步可独立验证）

| 步骤 | 内容 | 验证 |
|---|---|---|
| **S1** | 新增 `fat32_volume_scanner.v`（扩展匹配表）+ `fat32_file_streamer.v` + `sd_sector_adapter.v` | 单独 ModelSim 仿真：喂 FAT32 镜像，验证扫描器输出正确簇号/大小 |
| **S2** | `sd_card_bmp.v` 接入 FAT32：开机扫描器跑一遍 → 得到各文件簇号/大小，替代 Z_* 常量 | 综合通过 + 上板看能扫到素材 |
| **S3** | 图片加载改用 `fat32_file_streamer`（替代 bmp_read_auto 的扇区扫描，保留其 BMP 头解析/缩放/容错） | 上板图片正常 |
| **S4** | 会议配置 MTG1.CFG、音乐 WEL.BIN 改用流读器 | 上板会议议程 + 音乐正常 |
| **S5** | 全量回归 + 重扫 seed + 上板验证 + 固化 | preflight 全绿 |

## 五、风险与取舍

1. **文件名重命名是硬前提**：8.3 短名不支持长名。若坚持保留 `w1_320a.bmp` 这种长名，
   必须实现 LFN 解析（小鹅通明说"进阶内容，本节课不涉及"），复杂度大增。→ 建议重命名。
2. **扫描器局限**：小鹅通扫描器只读根目录**第一个簇**（128 项）。本工程素材 <20 项，够用。
3. **碎片化**：FAT 链读取后，素材可以碎片化存放，这是正规化的核心收益。
4. **改动量大**：约新增 680 行 + 改造 sd_card_bmp/bmp_read_auto 适配，风险中等。
5. **音频走 FAT 链的实时性**：48kHz 流式播放，FAT 链跨簇查表会引入读 FAT 扇区的额外延迟。
   需保证流读器吞吐 > 48kHz 消费速率（本工程音频占空比仅 ~5%，余量充足）。
